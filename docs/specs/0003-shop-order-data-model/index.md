# 0003. Shop and order data model

**Date**: 2026-09-18
**Status**: Accepted

## Summary

PrintFlow will use one relational model for the full pilot. Submitted configurations, prices, files, quotes, and customer decisions stay tied to exact immutable versions. Current states remain easy to query, while append only history explains every important change. The application will use `postgres@3.4.9` through Drizzle with separate pooled runtime and direct migration connections.

## Requirements

**User stories**:

1. As a customer, I want one order to contain several print jobs without later catalog changes altering what I submitted.
2. As a guest customer, I want to follow and approve my work through a private link without creating an account.
3. As the shop admin, I want exact current states, blockers, due dates, prices, files, notes, and history so that I can run production without a separate spreadsheet.
4. As the operator, I want retry safe writes and durable side effects so that crashes do not duplicate orders or lose required work.

**Acceptance criteria**:

1. **AC-1**: The schema represents shops, memberships, admin sessions, drafts, draft and order upload sessions, stored objects, catalog versions, orders, jobs, job revisions, artwork versions, proofs, quotes, customer decisions, internal notes, shop and order activity, privacy safe security events, encrypted capability delivery, access grants, idempotency, and outbox work with explicit shop ownership and valid foreign keys.
2. **AC-2**: A submitted job points to immutable service, price rule, configuration, measurement, and price resolution snapshots. A standard job stores its calculation, currency, tax, and rounded total. A quoted job stores `quote_required` until an accepted quote supplies those exact amounts. Publishing or retiring catalog versions cannot change historical jobs.
3. **AC-3**: One submitted nonterminal order contains one or more active jobs. Its known amount, pending quote work, blockers, and normal progress are derived from current job revisions and decisions, while cancellation and collection remain explicit order facts.
4. **AC-4**: Quote revisions are immutable complete replacements for every active quoted job and are itemized against exact job revisions. Adjustments allocate deterministically, each job rounds once, and the quote total equals the sum of job totals. Only the current sent revision may be accepted or declined. Expired, superseded, or stale revisions cannot be accepted, and concurrent conflicting responses produce one saved decision.
5. **AC-5**: Artwork replacements and proofs form immutable version chains. Draft and authorized order scoped uploads feed the same validated stored object path. Reviews and customer decisions name exact versions, and an affected artwork or commercial replacement makes the current proof and earlier approval stale before production may continue.
6. **AC-6**: Job production state is separate from quote and artwork blockers. Valid transitions, reversals, cancellation, readiness, and collection preserve the actor, reason, channel, and exact time in activity history.
7. **AC-7**: Orders preserve a contact snapshot without creating a customer account. Name and phone are required, email is required for online orders and optional for walk in or phone orders, and submission allocates one permanent shop and year scoped reference. Online access activates only after successful guest link delivery. Assisted orders without email create no guest grant.
8. **AC-8**: Money uses integer paisa and records `PKR`. SQL money maps to TypeScript `bigint`, JSON money uses decimal strings, and intermediate calculations use fixed point arithmetic without binary floating point. Each final job total rounds to the nearest rupee, and quote and order amounts sum those job totals. Measurements retain the entered value and unit plus normalized decimal millimetres. Exact times use UTC, requested dates use the shop local calendar, and the shop timezone is `Asia/Karachi`.
9. **AC-9**: Standard price acceptance, assisted acceptance, quote responses, proof decisions, production exceptions, corrections, internal notes, and meaningful mutations are append only facts with actor snapshots. No submitted commercial or approval record can be silently edited or deleted.
10. **AC-10**: Guest grants store only token hashes, carry narrow scopes, and support expiry, rotation, revocation, and last use. Invalid grants reveal no order existence. Private file access requires order authorization and a short lived signed URL.
11. **AC-11**: Business commands are shop scoped, safe to retry, and protected by expected aggregate versions. Canonical request fingerprints cover exact typed values. An identical retry returns its saved result or recoverable capability, a changed payload conflicts, and stale or invalid state changes return typed domain errors.
12. **AC-12**: A transaction that needs background work commits an outbox row with the business change. Fixed claims, lease fences, retries, dead state, and effect identifiers support crash recovery without creating a second logical effect.
13. **AC-13**: Submitted business history remains permanent. Catalog records archive instead of disappearing. File bytes become eligible for deletion 90 days after collection or cancellation, contact details and original filenames become eligible for erasure after 24 months, and the anonymous operating record remains readable.
14. **AC-14**: The schema and indexes support 100 orders per day, 20 jobs per order, 20 artwork versions per job, and five years of retained order history without table partitioning.
15. **AC-15**: A validated, idempotent server command bootstraps the pilot shop and its settings without placing production data in a migration.
16. **AC-16**: The application pins `postgres` to exactly `3.4.9`, `drizzle-orm` to exactly `0.45.2`, and `drizzle-kit` to exactly `0.31.10`. Runtime code creates one module scoped Postgres.js client from `DATABASE_URL` with one connection, prepared statements disabled, verified TLS, and bounded connection lifetime. Drizzle Kit uses a verified direct Supabase endpoint from `DATABASE_DIRECT_URL` for reviewed migrations and never uses a pooler.

## Decision

**Chosen option**: Option 1: Versioned relational aggregates with current projections

Use normalized Postgres relationships for business identity and ownership, immutable revisions for submitted facts, small validated JSONB documents for service definitions and calculation snapshots, and current projection columns for operational queries.

**PostgreSQL driver**: Pin `postgres@3.4.9`, `drizzle-orm@0.45.2`, and `drizzle-kit@0.31.10`. Use `postgres` through `drizzle-orm/postgres-js`. Create the runtime client once at module scope with `max: 1`, `prepare: false`, `connect_timeout: 10`, `idle_timeout: 20`, `max_lifetime: 300`, and verified TLS using the Supabase database certificate. Use the Supabase transaction pooler URL for `DATABASE_URL`. Reserve the direct Supabase endpoint in `DATABASE_DIRECT_URL` for Drizzle Kit migrations and other reviewed administrative commands. Do not create a client per request, run migrations through a pooler, or add `pg` beside Postgres.js.

**Implementation skills**: `drizzle` (`bobmatnyc/claude-mpm-skills`, `.agents/skills/drizzle/`) · `zod` (`pproenca/dot-skills`, `.agents/skills/zod/`) · `cloudflare-r2` (`secondsky/claude-skills`, `.agents/skills/cloudflare-r2/`) · `inngest-setup` (`inngest/inngest-skills`, `.agents/skills/inngest-setup/`) · `inngest-durable-functions` (`inngest/inngest-skills`, `.agents/skills/inngest-durable-functions/`)

Actor snapshots use the shared `actor_snapshots` relation. The allowed actor types are `admin`, `guest`, `assisted_customer`, and `system`. Structured JSON elsewhere uses `jsonb`, contains an explicit `schema_version`, receives a Drizzle TypeScript type, and is validated with the matching retained Zod schema at every write and historical read boundary.

All SQL monetary fields are signed 64 bit integers mapped to TypeScript `bigint`, with checks that final amounts remain nonnegative. JSON stores money as base 10 strings in paisa and never as JavaScript numbers. Canonical serializers convert `bigint` to those strings before JSON encoding and restore it only through a schema checked boundary. SQL `numeric` measurements remain decimal strings at the driver boundary. Raw SQL must use the same money and numeric mappers as Drizzle. Round trip tests include values above `Number.MAX_SAFE_INTEGER`.

Quantities and normalized measurements are positive numeric values. Email search values use trimmed Unicode NFC text with a lower case domain and local part. Phone search values use E.164, with `PK` as the parsing region only when no country code is present. Invalid or ambiguous numbers are rejected while the entered display value is retained. Search indexes cover shop plus reference, terminal state, due time, normalized contact fields, and creation time. Foreign keys and current pointer columns receive supporting indexes. Later list features use cursor pagination.

### Commercial calculations

`PriceCalculator` is a pure server contract. It accepts one published service definition, one published price rule definition, validated customer configuration, positive integer quantity, entered measurements, and the shop settings snapshot. It returns the normalized configuration, normalized measurements, calculation components, subtotal, adjustment, tax label, tax amount, and rounded total. Each calculation component names its rule and inputs so the snapshot is explainable.

Measurements use `numeric(18,6)` millimetres. Conversion constants are exact: one centimetre is 10 millimetres, one inch is 25.4 millimetres, and one foot is 304.8 millimetres. Intermediate money calculations use fixed point `bigint` with six decimal places below one paisa. Binary floating point is forbidden. A positive half rupee rounds up to the next whole rupee. The stored job total is therefore always a multiple of 100 paisa.

A standard job revision receives the complete calculator result before submission. A quoted job revision stores `pricing_mode = quote_required`, `PKR`, and a nullable unresolved amount until a current accepted quote names that exact revision. A pending or stale quote contributes an unknown amount, not zero.

A sent quote is a full replacement for the order's quoted work. It covers every active current job revision whose pricing mode requires a quote. Partial replacement quotes are not allowed. Sending a revision supersedes the earlier revision immediately and makes its acceptance historical before customer delivery begins.

A quote may contain several lines for each covered job revision. Line subtotal excludes line tax. Quote subtotal equals the sum of line subtotals, and quote tax equals the sum of line taxes. A quote level adjustment is allocated across covered jobs in proportion to their line subtotals. Integer remainders go to jobs in ascending order line number. If every subtotal is zero, the adjustment is split evenly with remainders in the same order. Each quoted job total is its line subtotals, allocated adjustment, and line taxes, rounded once to the nearest rupee. Quote total equals the sum of those rounded job totals. `rounding_delta` records the difference between that total and subtotal plus adjustment plus tax.

`getOrderAggregate` reports standard job totals, current accepted quoted job totals, the known order total, and the identifiers of jobs whose price remains unknown. Revising or canceling any covered job makes the full accepted quote stale and returns every active quoted job to unknown price until a complete replacement quote is accepted. The earlier acceptance remains historical.

### State transitions

Service and price versions use `draft` to `published` to `retired`. Published content never returns to draft and never changes. An order draft is revalidated against current published versions before submission.

Job production uses:

```text
draft -> received -> under_review -> ready_for_production -> in_production -> ready
```

Submission performs the first transition. Only an admin may perform later production transitions or an adjacent reversal, and a reversal requires a reason. Any nonterminal job may move to `canceled`. Cancellation is terminal. `ready_for_production` requires a resolved price, accepted current quote when needed, accepted required artwork, and an approved current proof when a proof is required.

An order is normally derived from its jobs. Its progress is the least advanced workflow state among active jobs. Blockers are returned separately by type and job. It is ready only when every active job is ready, all required price and artwork decisions are current, and at least one active job remains. Whole order cancellation cancels each active job in one transaction. Canceling the final active job also cancels the order in that transaction. The active job invariant applies only to submitted orders that are not terminal. Collection requires every active job to be ready and records one terminal order event. Partial pickup is outside the pilot.

Quote revisions use `draft`, `sent`, `accepted`, `declined`, `expired`, and `superseded`. Sending a new complete revision supersedes the earlier current revision and invalidates its accepted price immediately. A response transaction locks the current revision and compares the validity deadline with the database clock.

Artwork validation and proof approval remain separate from production state. Each job revision snapshots `quote_requirement`, required artwork purposes, required file checks, and whether proof approval is required. These values come from the published service definition plus any explicit admin override recorded with a reason.

A proof covers one exact job revision and the exact artwork versions in `proof_artwork_sources`. Creating it sets `jobs.current_proof_version_id`. Replacing any covered artwork version or creating a new commercial revision makes the current proof and its decision stale. A new commercial revision also makes standard acceptance and every quote tied to the earlier revision historical rather than current. Any of these changes creates a production hold immediately, including when the job is already in production or ready. The database does not pretend physical work reversed, but it blocks later transitions, order readiness, and collection.

`clearProductionHold` is the only ordinary way to clear a production hold. It requires an active admin, a reason, expected order and job versions, the exact current job revision, current artwork versions, current proof when required, and every current commercial and approval decision. It succeeds only when no required decision or safety check is missing, stale, quarantined, failed, or pending. It appends order activity and cannot use a production exception to bypass a safety or price blocker.

An effective correction is the highest numbered valid correction in a decision chain. Price acceptances, artwork reviews, proof decisions, and quote responses each use a sequence number unique to their exact target. A correction must point to the prior effective fact and target the current exact commercial, artwork, or proof version. An exception is effective only for an exact `proof_approval` blocker, becomes stale when that target changes, and stops applying at its optional expiry. Price, quarantine, validation, scanning, ownership, and terminal blockers are never eligible for an exception.

Terminal canceled or collected orders reject job revisions, new quotes, ordinary decisions, due date changes, production transitions, and grant rotation. Corrections, internal notes, retention erasure, outbox recovery, and operator audit actions remain allowed.

Catalog and quote content is immutable after publication or sending. Lifecycle columns are query projections maintained from append only lifecycle events. Quote expiry is effective whenever database time is past the deadline, even before a scheduled event records that observation.

### Server interface

No public HTTP route or Server Action belongs to this foundation. All interfaces below are server only functions. Every order command locks the order row first, checks its expected version, and increments that version with the committed mutation. A job version is an additional narrower check when one job changes. Catalog commands lock the service. Upload commands lock their upload session. Bootstrap uses its stable shop slug and caller idempotency key.

### Key invariants

1. A child and its parent always share `shop_id`. Composite foreign keys enforce this rule.
2. A submitted nonterminal order has at least one active job. A draft or terminal order may have none.
3. Submitted revisions, sent quotes, file versions, decisions, notes, activity, and outbox intent are immutable. Corrections append a linked fact. Explicit retention erasure may clear private contact values and original filenames, but it preserves anonymous metadata and appends an erasure activity.
4. A current pointer names a row in the same shop and aggregate. The pointer and new revision change in one transaction.
5. A submitted job revision names one published service version and one published price rule version. Retiring either later does not alter the revision.
6. A sent quote names every active current quoted job revision. Its adjustment allocation is deterministic, each covered job rounds once, quote total equals the rounded job totals, and no amount can be negative.
7. Normal order progress and totals are derived. They are not stored as a second mutable source of truth.
8. A job cannot enter production while a required price, artwork, or proof decision is missing or stale. A production exception may bypass only the exact current `proof_approval` blocker and never a price or safety blocker.
9. Only the first valid ordinary response to a current quote or proof becomes effective. Identical retries return it, while conflicts fail. A later correction is a separate admin recorded fact and never edits the original response.
10. One logical user intent has one idempotency record and result. A processing lease may be reclaimed only after expiry.
11. A business mutation and every required outbox event commit or roll back together.
12. Raw guest tokens, provider credentials, and private signed URLs never enter business tables or logs.
13. Every order mutation locks the order first and increments `orders.version`. Commands that change one job also check and increment `jobs.version`. Replayed commands recheck current authorization before returning the saved safe response.
14. Quote lines, proofs, decisions, current pointers, and price rules must belong to the same order, job, or service named by their aggregate. Same shop ownership alone is not sufficient.
15. Production exceptions may bypass only a documented business approval blocker. They cannot bypass quarantine, byte limits, format validation, a required failed or pending scan, cross shop ownership, or terminal order rules.
16. Ordinary commands create and complete their idempotency record in the same database transaction as the business result. A rollback leaves no partial result. A leased processing record is used only when durable prework must span transactions, and it may be reclaimed after expiry only for the same canonical request fingerprint.
17. SQL money maps to TypeScript `bigint`. JSON money is a decimal paisa string. JavaScript `number` never crosses a money boundary, and raw SQL uses the same mapping contract.
18. Immutable tables deny update and delete to the runtime role. Current projections permit only their named transitions. Retention fields live in designated private value tables or columns whose constraints allow only erasure, never replacement.

### Security model

Business tables live in the private `app` Postgres schema. Browser roles and Supabase Data API roles have no schema usage or table grants. `printflow_app` is the constrained runtime role. It may use current projection tables and append facts through the server domain layer, but immutable tables deny update and delete. `printflow_migrator` owns schema changes and is available only through the direct migration connection. `printflow_backup` has read access for backups and no application login. Every domain entry point authenticates its admin session or validates a scoped guest grant, resolves the shop on the server, and includes `shop_id` in every query.

Database foreign keys, unique constraints, checks, grants, and immutable table permissions enforce structural rules. Transaction services enforce aggregate state transitions and acquire locks. The database repeats critical state checks in constrained updates so stale code cannot bypass versions or shop ownership. Retention erasure can only replace an allowed private value with null and set its erasure time. It cannot alter anonymous history.

An active shop membership authorizes admin work. Guest grants authorize only their recorded order and scopes. Invalid, expired, or revoked grants return the same generic not found result and append a privacy safe security event. Admin identity comes from Supabase Auth, never from user editable metadata.

Admin sessions bind the hashed Supabase session identifier to one active membership, retain original sign in time, and expire absolutely after seven days. Logout, recovery, membership removal, and operator revocation invalidate them. A guest token has 32 random bytes. Recovery creates a pending replacement, activation waits for accepted email delivery, the old token receives a 15 minute grace period, and a failed delivery deletes the replacement without disturbing the current grant. Active grants expire 90 days after cancellation or collection.

Guest scopes are `order:read`, `artwork:upload`, `quote:respond`, `proof:respond`, and `link:rotate`. The guest read projection includes the order reference, submitted contact display, customer visible job configuration, price summary, due information, public progress, blockers that need customer action, customer messages, and customer visible activity. It excludes internal notes, admin identities, security events, idempotency, outbox data, private file keys, other contact search values, and every other order.

Only an admin records artwork review and selects production artwork. A guest with `proof:respond` or an admin recording an assisted customer response records proof approval. A guest with `quote:respond` or an admin recording an assisted response accepts or declines a quote. Only an admin may append a correction or production exception, and the correction retains the original customer identity and channel.

R2 objects remain private. File reads require business authorization before the server creates a five minute signed URL. Quarantine, authoritative object metadata, signature validation, and the file lifecycle from spec 0001 remain mandatory. A file whose required scan is pending or failed cannot be reviewed or used in production.

Contact details and original filenames are private customer data. Application logs and monitoring omit them, along with raw tokens and file contents. The pilot has no named regulatory framework, but least privilege, explicit retention, and secure erasure apply.

Private customer values may exist only in typed columns that declare their retention behavior. Generic activity details, idempotency snapshots, quote calculation JSON, and ordinary outbox payloads reject contact values, actor contact details, raw tokens, original filenames, and free form file metadata. Customer actor labels become `Guest customer` or `Assisted customer` during the 24 month erasure job. Original names in stored objects and proof objects are erased at the same boundary. Anonymous actor type, channel, decisions, amounts, configuration, measured file metadata, and timestamps remain.

Internal notes and customer messages are retained operational text, so their input guidance forbids copying contact details or filenames into them. The application cannot promise automatic removal from arbitrary prose. Temporary encrypted guest link payloads are a distinct outbox payload type and are erased after accepted delivery or 24 hours. Byte deletion covers artwork and proof objects, records the deletion time and outcome, and keeps measured anonymous metadata.

### Configuration required

1. `DATABASE_URL`: Supabase transaction pooler connection for `printflow_app` runtime commands. The shared pooler uses transaction mode on port `6543`. Store it only in Vercel encrypted server variables.
2. `DATABASE_DIRECT_URL`: Supabase direct `db.<project-ref>.supabase.co:5432` connection for `printflow_migrator`. Store it only in the reviewed migration environment. It must never be available to application runtime or browser code.
3. `DATABASE_CA_CERT`: Supabase database root certificate in PEM form. Runtime and migration clients use it for certificate and hostname verification.
4. `LINK_PAYLOAD_ENCRYPTION_KEY`: existing 32 byte application secret from spec 0001, now used for both draft capability recovery and guest link delivery. Store its key version with each ciphertext.
5. `NEXT_PUBLIC_SUPABASE_URL`: existing browser safe project URL from spec 0001. Migration validation derives the expected project reference from it.
6. `SHOP_ID`: existing configured pilot shop identity after bootstrap.
7. Bootstrap input: validated shop profile and settings, including `PF`, `Asia/Karachi`, `PKR`, quote validity days, and the fixed rounding rule. This is business data, not a secret.

### Database connection behavior

The server imports one shared runtime database module. That module creates one Postgres.js client and one Drizzle instance for each warm application process. It does not connect eagerly during module import, create a pool per request, or close the shared client after a request.

The runtime client uses `DATABASE_URL` with `max: 1`, `prepare: false`, `connect_timeout: 10`, `idle_timeout: 20`, `max_lifetime: 300`, and the CA certificate with hostname verification. The pool limit is per warm process, not global. Concurrent database work inside one process may wait for that one connection. Raise it only after measured queue time proves a need and the Supabase connection budget is reviewed.

The connection points to Supabase transaction mode because Vercel functions can create many short lived instances. Prepared statements remain disabled because transaction mode can assign consecutive transactions to different database sessions. Code must not rely on session scoped `SET`, temporary tables, session advisory locks, or `LISTEN` through this connection. `NOTIFY` is also outside this design even though it does not require a persistent subscription by itself.

Drizzle Kit reads only `DATABASE_DIRECT_URL`. Migration scripts derive the expected project reference from `NEXT_PUBLIC_SUPABASE_URL` and fail before network access unless the parsed host is that project's `db.<project-ref>.supabase.co` endpoint on port `5432`, the role is `printflow_migrator`, and the CA certificate is present. Every pooler hostname and port is rejected. Migrations run from an operator controlled environment with tested IPv6 access. If that environment lacks IPv6, the operator must provide the Supabase IPv4 add on before migration. Production migrations run as a separate reviewed command, never during application startup or a request.

Application transactions use Drizzle's transaction API so the order change, activity, idempotency result, and outbox intent share one checked database transaction. A connection lost before commit returns a retryable infrastructure failure. A connection lost during or after commit returns an unknown outcome, so the caller retries only through the same idempotency key. The client may reconnect after idle closure, but code never replays a transaction automatically.

### Operational behavior

The dispatcher follows spec 0001 and `src/jobs/AGENTS.md`. It runs each minute, claims at most 100 committed rows with `FOR UPDATE SKIP LOCKED`, increments the outbox lease fence, and uses a five minute lease. Attempts occur at event time, then no earlier than 1 minute, 5 minutes, 15 minutes, 1 hour, 3 hours, 8 hours, and 24 hours after the first attempt. Exhausted work remains in `dead` state for alerting and manual retry. A worker with an older fence cannot record completion. Completed idempotency records remain for 30 days. A leased idempotency record uses a five minute lease and may be reclaimed only with the same fingerprint.

The committed event registry owns every event name, Zod payload schema, active email template version, and customer visibility rule. The initial customer email allowlist is order confirmation, quote delivery, proof delivery, `in_production`, `ready`, `canceled`, and `collected`. Other state changes appear in the authorized guest view but do not send email. File acceptance and rejection are operational events. A job revision emits customer action work only when the new current facts require a quote response, proof response, or replacement artwork.

Each event schema contains identifiers and the minimum nonprivate display values its consumer needs. Before a provider call, the worker appends an `external_effect_attempts` row. A lost response becomes `uncertain`; the next attempt must query or otherwise reconcile the provider with the stable outbox identifier before sending again. Test consumers use a deterministic fake provider that can accept an effect and drop the response.

| ------------------------------------------ | ------------------------------------------------------------------------- |
| `order.confirmation_requested.v1`          | order, pending grant, template version, encrypted link payload identifier |
| `quote.delivery_requested.v1`              | order, quote revision, active grant, template version                     |
| `quote.response_recorded.v1`               | order, quote response, template version                                   |
| `proof.delivery_requested.v1`              | order, job, proof version, active grant, template version                 |
| `proof.response_recorded.v1`               | order, job, proof decision, template version                              |
| `order.visible_status_changed.v1`          | order, optional job, activity entry, template version                     |

| `artwork.review_requested.v1`              | order, job, artwork version, activity entry                               |
| `access.replacement_delivery_requested.v1` | order, pending grant, template version, encrypted link payload identifier |

Consumers load contact destinations and approved customer display data from the authorized aggregate at execution time. The event payload never duplicates them. Each schema is a strict versioned Zod object, and unknown fields are rejected.

The initial schema registry contains `service_definition.v1`, `price_rule.v1`, `calculation_snapshot.v1`, `event_payload.v1`, and `idempotency_response.v1`. The tracer bullet uses a test only `test_standard_v1` service and rate rule with explicit seeded values. Those rates never enter production migrations or bootstrap data. Production catalog values come only from validated operator input and the shop's real rate cards.

A blocker identifier is the canonical tuple of blocker type, exact target table, and target identifier. The initial blocker types are `price_acceptance`, `quote_response`, `artwork_review`, `proof_approval`, `file_validation`, `file_scan`, and `production_hold`. Only `proof_approval` is eligible for a production exception. The event registry and blocker registry are exhaustive TypeScript records, so adding a type requires its schema and handling at compile time.

Structured logs and metrics cover command failures, stale versions, invalid transitions, guest grant failures, quarantined files, outbox lag, lease recovery, and dead events. Logs use correlation, order, job, and event identifiers without private contact data or tokens.

Routine aggregate reads load current jobs, current revisions, current decisions, and current price facts only. Artwork history, full activity, notes, and outbox records use separate cursor paged reads. Capacity verification uses statistics equivalent to five years at 100 orders per day, an expected average of two jobs and two artwork versions per job, and the agreed per order maxima of 20 jobs and 20 artwork versions per job. Representative order, due queue, reference, contact, and activity queries must use their intended bounded indexes. The design does not add partitions until measured query plans require them.

## Consequences

**Positive**:

1. Historical orders remain exact even as services, prices, files, and customer decisions change.
2. Current queue reads stay straightforward because operational projections do not require event replay.
3. Explicit shop ownership, membership, and access grants preserve the future paths to more shops and identities.
4. Transactions, idempotency, and the outbox give later user journeys safe failure behavior from their first write.
5. One small driver serves both Drizzle queries and explicit SQL, while its runtime settings match Supabase transaction pooling.
6. Fixed money mapping and canonical JSON prevent silent precision loss across SQL, JSON, retries, and background work.

**Negative and tradeoffs**:

1. The foundation creates many tables before every pilot surface uses them.
2. Immutable revisions and current pointers demand careful transaction code and more joins than mutable records.
3. Versioned JSON schemas must remain readable for the lifetime of retained history.
4. Direct `shop_id` columns and composite foreign keys repeat ownership data, but that repetition prevents cross shop relationships and supports future isolation.
5. Disabling prepared statements gives up their possible repeated query benefit, but avoids invalid session assumptions under transaction pooling.
6. One connection per warm process serializes concurrent database work in that process. This is deliberate for the pilot and must be measured before increasing it.
7. Direct migrations require IPv6 reachability or the paid Supabase IPv4 add on, plus management of the Supabase database certificate.

**Neutral**:

1. This spec defines persistence and server domain contracts. It does not build customer pages, admin pages, price formulas, upload transport, email content, or background consumers.
2. Customer accounts, staff role design, payments, delivery, inventory, and automatic print readiness checks remain outside the pilot.
3. Later feature specs may add indexes or new append only facts, but they may not weaken the immutable history and ownership rules here without superseding this decision.
4. The driver is pinned exactly. Dependency upgrades require an explicit change, lockfile review, and the real database connection scenario.
5. Quote revisions replace the full quoted bundle. A change to one covered job requires a new complete quote, which favors clarity over partial commercial updates.
